# Agentic PDF specification

## Purpose

Build an open-source desktop PDF reader for macOS and Windows using Rust, GPUI, and PDFium. Prioritize fast document opening, responsive navigation, and bounded memory. Measure performance rather than assuming it.

## Implemented scope

- Open multiple local PDFs through the native file picker, external file drops, the command line, or Finder (Open With, and double-click when Agentic PDF is the default viewer). On macOS the bundle declares PDF as a viewable document type, and files sent while the app is running open as tabs in the existing window.
- Serve read-only PDF tools to AI agents with `agenticpdf mcp`, a Model Context Protocol server over stdio built on the official rmcp SDK: `document_info`, `get_outline`, `get_text` (bounded by `max_chars` with a `next_page` cursor), and `search`. It accepts any `.pdf` path, never writes, reports pages without a text layer instead of skipping them, runs PDFium on one dedicated thread, and keeps at most four documents open. Attaching to the running reader and the in-app agent panel are planned in issue 18.
- Remember up to 20 recently opened files with their last page and zoom, restore both on reopen (clamping to the last page if the file has shrunk), and list them in File > Open Recent and on the empty screen. Files that no longer exist are removed when chosen. The list is stored locally in `recent.tsv` under Application Support (macOS) or `%APPDATA%` (Windows), separately for debug and release builds, and is written atomically on open, tab switch, tab close, and quit.
- Show documents in tabs and focus an existing tab when its canonical path is reopened.
- Preserve each tab's page, zoom, canvas scroll, and sidebar scroll position.
- Display one page at a time with previous/next navigation, zoom, and fit-to-width.
- Provide a collapsible virtualized thumbnail sidebar.
- Select text on the current page by dragging; copy with the toolbar or platform shortcut.
- Go to a page with Cmd G (Ctrl G on Windows) or the page field, and to the first or last page with Home and End or Cmd Home and Cmd End.
- Support select-all on the current page and Escape to clear selection.
- Search the whole document from the find bar (Cmd F, Ctrl F on Windows): case-insensitive by default, with Match case and Whole word options. Matches span line breaks and fold Unicode case. Enter and Shift+Enter, the arrow keys, or the bar's buttons step between matches and move to their page. Matches on the visible page are highlighted, the bar shows the position ("3 of 41"), and the Results panel lists matches by page with surrounding text.
- Fit the whole page in the window (Cmd 9, Ctrl 9 on Windows) or show it at actual size (Cmd 1). Fit page sets a zoom percentage once from the current window and page; it does not follow later window resizes.
- Bookmark the page you are reading (Cmd D, or Add in the Bookmarks panel) and remove the bookmark the same way. Bookmarks are listed with the page's first line of text, marked on thumbnails, kept on this computer in `bookmarks.tsv`, and never written into the PDF. At most 500 per document and 200 documents are kept.
- Settings that persist in `preferences.conf`: theme, default layout, default zoom for newly opened files (fit width, fit page, or 100 percent), whether a file reopens at the last page read (on by default), whether the last session's tabs reopen on launch when no file is given (off by default, at most 50 tabs, missing files skipped), and whether marks save automatically two seconds after the last change (off by default).
- View pages two at a time, as plain pairs or with the first page alone as a cover. Both are continuous layouts and are remembered as the default layout.
- Show pages in night colours (light text on a dark page) or sepia from the View menu. Settings choose whether night pages are never used, follow a dark theme, or are always on. Colours are applied to the rendered bitmap; thumbnails and saved files are unchanged.
- Magnify the area under the pointer two times in a loupe (Cmd Shift M; Escape closes it). The loupe scales the page image already on screen, so it is softer than a true higher-resolution render, and it does not show unsaved marks.
- Present the document full screen on a black background (Cmd Shift P): one page fitted to the screen, Left and Right to move, Escape to leave. Layout, zoom, sidebar, and panels are restored on exit.
- Organize pages (Cmd Shift O): select pages, rotate them left or right, delete them, add every page of another PDF at the end, and extract the selection to a new PDF. Changes show in the thumbnails at once but stay in memory until Apply (or Cmd S) writes the file; Cancel, Escape, or switching tabs discards them. Deleting every page is refused. "Rotate current page" in the command palette rotates and saves in one step. Organizing starts only from a saved document, so unsaved marks must be saved or undone first. Pages cannot be reordered yet.
- Mark selected text as a highlight, underline, or strikethrough in one of four colours: from the selection bar, the Annotate tool bar (dragging with a markup tool marks on release), the command palette, or the inspector. Marks span pages with the selection, are listed in the Notes panel for the session, and can be undone and redone (Cmd Z, Cmd Shift Z; Ctrl on Windows) until saved.
- Add a drawn signature: draw it in the Add signature dialog in one of three inks, then place it on the current page. A placed signature is selected, with a dashed outline and corner handles: drag it to move it, drag a corner to resize it with its shape locked, press Enter or click elsewhere to finish, or Escape to remove it. Signatures share undo, redo, the Notes panel, and save with text marks, and are visual only: no certificate is involved. Typed and image signatures and saved signatures are not built.
- Save marks and signatures into the PDF as standard annotations with Cmd S (Ctrl S on Windows). The file is rewritten next to the original and swapped in atomically; read-only and digitally signed PDFs are refused and left unchanged. A tab with unsaved marks shows a dot, and closing it, closing the window, or quitting asks first.
- Transform text geometry to match rotated pages and preserve Unicode and line breaks when copying.
- Report file, rendering, and text extraction errors without terminating the reader.

OCR, notes, freehand drawing on the page, shapes, text boxes, stamps, typed, image, saved, and certificate signatures, listing or editing annotations already in a PDF, password entry, document editing, signed installers, and Windows distribution packaging remain out of scope for this version.

## Naming

The product is Agentic PDF. Until 0.1.4 it shipped as PDF Reader. From 0.2.0 the bundle is `Agentic PDF.app` with identifier `app.agenticpdf.desktop`, the executable is `agenticpdf`, release files are `agenticpdf-<platform>.zip`, environment variables start with `AGENTICPDF_`, the MCP server reports the name `agenticpdf`, and the repository is `joelfickson/agenticpdf`. The domain chosen for the site is agenticpdf.app; it is not registered or attached yet, so links still point at the Vercel address.

On first launch the app copies `recent.tsv` and `updates.conf` from the former data folder (`org.pdfreader.desktop` on macOS, `PDF Reader` under `%APPDATA%` on Windows) when the new folder does not exist yet. It never overwrites newer settings and leaves the former folder in place.

Installs of 0.1.4 and earlier look for the former release file names and, on macOS, require the former bundle identifier, so they do not update themselves to 0.2.0 or later. Six downloads of 0.1.4 were recorded across the three platforms when this was decided.

## Architecture

The binary entry point handles arguments. app.rs owns window startup, native menus, and key bindings. reader/ owns window state, per-document tabs, navigation, selection, caching, scheduling, and view composition. pdf/ owns PDFium discovery, rasterization, text extraction, and the background worker.

Unsaved marks live in the tab as page-normalized rectangles and are painted over the page; they are bounded at 2,000 per document. Saving queues a job that is never replaced by newer render requests: the worker drops its cached handle for that document, reopens the file, adds the annotations in page coordinates (inverting the same geometry used for text, so rotated pages work), writes a sibling temporary file, and renames it over the original. The reader then discards that document's cached page images and thumbnails so PDFium's rendering of the saved annotations replaces the overlay.

A drawn signature is kept as strokes normalized to their own bounding box plus a page-normalized rectangle, so moving and resizing change only the rectangle. The drawing pad holds at most 20,000 points. On save each signature becomes a stamp annotation whose appearance is the strokes as vector paths with round caps and joins, in page coordinates, with a stroke weight proportional to the signature's width.

Page changes are applied to a document handle the worker keeps apart from its four-handle cache, so it is never evicted while changes are pending and every render, thumbnail, and search for that tab sees the changed pages. Apply saves that handle to a sibling temporary file, drops the handle, and renames the file over the original, the same replacement used for saving marks. Read-only and digitally signed PDFs are refused. Extracting copies the chosen pages into a new document and does not count as a change.

PDFium runs on one dedicated worker thread. A single pending request replaces obsolete work; generation identifiers reject stale results. Main-page rendering precedes text extraction and thumbnail rendering. In-progress native calls are not forcibly interrupted.

Search has its own slot and generation on the same worker thread, so render requests never cancel it. The worker scans pages in slices of at most 30 ms and yields to any pending render job or newer search between pages. Matching runs on page characters only and returns glyph ranges that index the same glyphs as text extraction, so highlights reuse the page text cache. A search stops at 5,000 matches; pages over the 100,000-character text cap are skipped and reported. The Results panel lists the first 200 matches.

The worker retains up to four document handles and reopens evicted handles lazily. Shared caches retain up to eight previous page images within 64 MiB, 64 thumbnails within 16 MiB, and text for 32 pages within 16 MiB. The active page and other engine/GPU allocations consume additional memory. Text extraction is capped at 100,000 characters per page. Closing a tab releases its cached content and document handle.

## Interface

Use a warm neutral canvas, compact toolbar and tab strip, blue interaction accent, collapsible sidebar, and ample reading space. Group controls with whitespace, typography, alignment, and hairline rules. Approved design mocks are kept locally in an ignored design/ folder and are not committed.

## Validation

Formatting, strict Clippy, and 124 tests (12 of them PDFium-backed and ignored by default) pass locally on macOS. Tests cover bounded caches, request cancellation, document-handle reuse and eviction, malformed-file recovery, Unicode text, rotated geometry overlapping rendered ink, image-only pages, and search matching (line breaks, Unicode case, whole word, match case, limits) against both synthetic text and the PDFium fixture, including a page render submitted mid-search. GPUI interaction tests cover the external-drop event route, path filtering and deduplication, selection and clipboard actions, stale-event rejection, cached and uncached tab scroll restoration, tab closing, the find flow (debounced search, stale-result rejection, stepping and wrapping between matches, option changes, and clearing on close), and recent files (position restore, clamping, recording on close, pruning missing files, clearing). Unit tests cover the recent-file store (ordering, cap, round trip, malformed lines, unreadable store), file URL decoding, and the Open Recent menu.

Marking and saving are covered at three levels on macOS. Unit tests cover merging glyphs into one rectangle per line (including vertical text) and inverting the page geometry. PDFium-backed tests save a highlight on an upright page and on a rotated page plus an underline to a copy of the selection fixture, reopen it, and check the annotation types and that the highlight tints the marked text in the rendered page while an unmarked region stays untinted; that a read-only file is refused and left byte-identical with no temporary file behind; and, through the worker's own queue, that a save is answered and the next render of that document shows the highlight. A GPUI interaction test covers marking from a selection, marking on release with a markup tool in Annotate mode, undo and redo, the save request, refusing edits while saving, scroll restoration after the post-save refresh, a failed save keeping the marks, and the Save, Discard, and Cancel answers when closing a tab with unsaved marks. The debug build, run on a fixture copy through its preview hook, wrote one highlight and one underline annotation into the file. The live window was not inspected visually, the rendered position of underline and strikethrough was not pixel-checked, the signed-PDF refusal has no signed fixture, and none of this has been run on Windows.

Signatures are covered the same way. Unit tests cover normalizing strokes to a unit box and moving and resizing within the page with the shape kept. A PDFium-backed test saves a signature onto an upright and a rotated page of the selection fixture, reopens it, and checks that each page gains one stamp annotation, that ink appears inside the signature's rectangle, and that the regions to its left, right, above, and below render exactly as before. A GPUI interaction test draws on the pad with mouse events, clears and redraws, places the signature, drags it, resizes it from a corner, confirms with Enter, undoes and redoes, cancels a second placement with Escape, finishes a third by clicking elsewhere, and requests a save. The debug build, run on a fixture copy through its preview hook, wrote one stamp annotation into the file. The drawing pad, the outline and handles, and stroke smoothness were not inspected visually, and none of this has been run on Windows.

Settings, sessions, and bookmarks are covered by unit tests for their file formats (round trips, unknown keys, bounds, paths that cannot be stored) and for the fit-page calculation, and by GPUI interaction tests for the default zoom on open, fit page waiting for the first page image, the last-page setting, bookmark titles and toggling, autosave firing two seconds after the last mark and not before, and reopening a saved session while skipping a missing file. None of it was inspected in the live window.

Page organizing is covered by a PDFium-backed test through the worker's queue: a rotation changes the rendered page's shape while the file stays byte-identical, Cancel restores it, deleting every page or a missing page is refused, then a delete, an insert from another fixture, a two-page rotation, and an extract are applied and written, after which the file reopens with five pages and the extracted file with two. A GPUI interaction test covers refusing to organize with unsaved marks, the queued operation for each button, refusing to delete every page, the extract save dialog, a failed Apply keeping the changes, Escape discarding, Apply leaving the mode, and the one-step rotate command. The file pickers for insert and the live Organize screen were not exercised by hand.

View modes are covered by unit tests for the two-page layout (pairing, cover first, centring an odd last page, and keeping both pages of a row visible, including when the window starts in the gap between rows) and for night and sepia tinting of pixels, and by a GPUI interaction test for changing page colour, the night-pages setting, switching layouts, entering and leaving presentation with its state restored, and the magnifier following the pointer. How any of these look was not checked in the live window.

The installed macOS release bundle appears in Open With for PDFs. Opening a PDF through Launch Services (`open -a`, which sends the same open-documents event as Finder) opened it when the app was closed, and opened a second file as a new tab in the same process while it was running. Quitting wrote `recent.tsv`, a relaunch listed both files under Recent, and reopening a file with a stored position restored page 3 at 125 percent. Double-clicking was not tested, because it requires making Agentic PDF the default PDF viewer.

The packaged macOS engine opens and renders the authored fixtures. Full native interaction verification for the tabs/selection build remains incomplete because desktop automation loses window access after the native picker closes. Windows runtime validation is pending. CI is configured for macOS and Windows; compilation and unit tests alone do not establish Windows runtime behavior.

The MCP server was measured on an Apple M1 Max (32 GB) with Rust in Action (457 pages, 18 MB), release build, driving `agenticpdf mcp` over stdio from a Python client, three runs: initialize answered in about 8 ms once warm (309 to 540 ms on the first cold launch), `document_info` scanned all pages in 391 to 429 ms, `get_outline` returned 336 entries in 13 to 15 ms, `get_text` returned 17 pages (19,718 characters) in about 7 ms, and `search` found 125 matches in 355 to 365 ms. Adding the server grew the release binary from 9.39 MB to 11.83 MB. Claude Code 2.1.319 used the server through `--mcp-config` to read the outline fixture, find a phrase split across a line break, and report a page without text.

Search was measured on an Apple M1 Max (32 GB) with Rust in Action (457 pages, 18 MB), release build, using a temporary worker harness timing submission to completion over three runs: a full scan took 425 to 620 ms, the first matches arrived after about 40 ms, a 5,000-match query stopped at the cap after about 300 ms, and a page render submitted mid-search completed in 11 to 18 ms including render time.

Time to first page was measured on an Apple M1 Max (32 GB, macOS 27.0), release build, with `uv run scripts/bench_first_page.py`: one warm-up launch and five measured launches per document, each with an empty Recent list. The app reports, from the start of `main` until the first frame that paints the page, and the script reads the process's peak resident memory from `wait4`. Medians (range): the 3-page fixture 253 ms (247 to 261), 148 MB; generated 500 pages 262 ms (240 to 269), 148 MB; generated 2,000 pages 258 ms (248 to 275), 148 MB; C and GUI Programming (156 pages, 7.5 MB) 260 ms (256 to 273), 170 MB; Rust in Action (457 pages, 18 MB) 287 ms (283 to 295), 184 MB. Page count does not change the result. About 250 ms is spent before any page can be shown: GPUI is ready after about 75 ms, the window after about 150 ms, and the first frame (the loading view, including GPU setup) holds the main thread until about 250 ms, so a page rendered earlier waits for it. The document opens and its first page starts rendering before the window finishes opening. PDF work is on the critical path only when the first page takes longer than about 100 ms to render: Rust in Action's cover renders in about 130 ms at 2x. A test render at 1x took about 110 ms and moved the first paint from about 305 ms to about 270 ms in that build; a low-resolution first render was not adopted because it saves about 35 ms on such pages, nothing on others, and costs a second full render and a visible swap. Thumbnails already render after the page and text, so deferring them does not change the first paint.

Continuous scrolling was measured on the same Apple M1 Max (120 Hz display), release build, with `AGENTICPDF_BENCH=scroll` scrolling the whole document at 120 px per frame inside `/usr/bin/time -l`, one run each: generated 500 pages took 4,894 frames with a median interval of 8.33 ms, 95th percentile 8.66 ms, maximum 13.6 ms, no frame over 33 ms, 42 frames showing a page before its image was ready, and 344 MB peak resident memory; generated 2,000 pages: 19,587 frames, median 8.33 ms, 95th percentile 9.39 ms, maximum 21.5 ms, none over 33 ms, 581 frames with an unrendered page, 387 MB; Rust in Action (457 pages): 4,348 frames, median 8.33 ms, 95th percentile 9.97 ms, maximum 22.8 ms, none over 33 ms, 75 frames with an unrendered page, 492 MB. Memory does not grow with page count: four times as many pages added 43 MB. Rendered pages stay inside the existing caches (8 pages and 64 MB of page images, 32 pages and 16 MB of text).

Engine-only inspection reports initialization, parsing, rendering, and bitmap size. It does not measure time until a page is visible or total process memory. Performance reports must name the machine, document, measurement method, and memory metric.
